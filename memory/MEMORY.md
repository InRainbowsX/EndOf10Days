# 工程记忆

## 目的

本目录存放会跨任务复用的工程规则，不记录一次性闲聊，不记录没有防线的经验。

## 长期规则

### 开发模式

- 不要对 Issue 做条件反射：先理解业务场景，再设计测试用例，最后才写代码
- 先学习研究：查看现有代码了解已有资源，再修改
- 业务场景优先：测试用例应该描述“是什么”，而不是“怎么实现”

### 仓库勘察

- 开始分析前先执行 `git status --short --branch`
- 扫描仓库文件时，默认使用能包含隐藏目录的方式，例如 `find` / `rg -uu --files`
- 涉及工程治理时，必须显式检查：
  - `AGENTS.md`
  - `docs/AGENTS.md`
  - `memory/`
  - `.github/workflows/`
  - `scripts/`
  - Docker 相关文件

### 变更闭环

- 每个真实错误都要补三件事：案例记录、长期规则、自动化防线
- 修复 bug 时，优先补回归测试
- 新增流程时，优先补脚本或 CI，而不是只加 README

### 工程验证

- 仓库级交付前必须执行 `./scripts/run_checks.sh`
- CI 至少覆盖 `lint`、`test` 和 `build`
- 治理文件缺失应被测试直接发现

### 当前仓库特定规则

- 人物馆的画布要以边界和碰撞约束为准，不接受仅靠“视觉上差不多”的实现
- 事件馆必须保持时间轴顺序，不能为了展示牺牲主脉络
- 世界观馆必须优先保证分类口径清晰，再考虑装饰
- 研究池、清单层、正式层、记忆层必须分层；正式页面只消费正式层或明确标记为 `待核` 的过渡数据
- 可选且依赖本机能力的重型库不要在模块顶层直接引入，应按需懒加载并在失败时优雅降级

## 何时更新本文件

满足任一条件就应该更新：
- 同类错误第二次出现
- 某次错误暴露了通用检查缺口
- 某条规则已经被脚本、测试或 CI 固化

## 配套文件

- `memory/incidents.md`: 具体错误案例
- `memory/templates.md`: 记录模板
- `memory/development.md`: 开发过程与工程规范
